# 0006. Входящие документы на LangGraph с решением человека

**Статус:** принято

## Контекст

Водители и подрядчики присылают фото и PDF: постановления ГИБДД, счета СТО, права кандидатов. Часть документов можно провести без человека, часть — нет: сумма больше сметы, документ уже приходил, машина в тот день не была в аренде. Решение человека может прийти через час или на следующий день, а сервер за это время может перезапуститься.

## Решение

- Конвейер — `StateGraph` из шести узлов (`app/inbox_graph.py`): `read → classify → validate → review | post`, `review → post | reject`.
- `review` вызывает `interrupt()`. Состояние хранится в PostgreSQL (`langgraph-checkpoint-postgres`, схема `langgraph`). Решение из кабинета ставит задание, воркер продолжает тот же `thread_id` через `Command(resume=…)`.
- В состоянии графа только id документа и решение. Сам документ, поля, проверки и шаги с замеренным временем лежат в `items` — их показывают кабинет и консоль.
- Чтение: текстовый слой PDF — правилами, бесплатно. Фото и сканы — vision-моделью через общий слой ИИ с бюджетом; не больше 5 таких документов в сутки на демосессию.
- Проводка — через тот же учёт и те же команды, что в кабинете. Штраф — начисление водителю по договору на дату нарушения. Счёт СТО закрывает ремонт командой `ticket.complete`. ВУ создаёт карточку кандидата на проверку.
- Граф запускается коротким подпроцессом воркера, поэтому библиотеки LangGraph не держат память постоянно (как и эмбеддинги, ADR 0004).

## Последствия

- Документ, остановленный на решении, переживает перезапуск сервера.
- Повторное нажатие или повтор задания не проводят документ дважды: ключ идемпотентности `inbox:<id>` у проводки и у команды.
- Подпроцесс добавляет 1–2 с к обработке документа — для входящих документов это приемлемо.
