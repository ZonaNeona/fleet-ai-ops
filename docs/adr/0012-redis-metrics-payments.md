# 0012. Redis — ускоритель, а не источник правды; платежи проводятся только после перечитывания у провайдера

**Статус:** принято

## Контекст

Стенду нужны лимиты запросов, быстрые повторные отчёты и живая лента без опроса базы. Нужны метрики для
Prometheus и онлайн-оплаты долга, залога и штрафов. Сервер — 4 ГБ на несколько проектов.

## Решение

### Redis
- **Лимиты:** фиксированное окно `INCR` + `EXPIRE`; ключ — солёный хеш IP. Адрес берётся из последнего значения
  `X-Forwarded-For`, которое дописывает nginx; заголовок от клиента подделать нельзя. Соль живёт в процессе, по
  хешу адрес не восстановить. Лимит на запись — на посетителя, отдельный — на создание сессий; у вебхуков
  провайдеров свои проверки, лимит к ним не применяется.
- **Кэш отчёта:** ключ включает «поколение» пространства. Любой коммит, задевший объекты, проводки или события
  пространства, увеличивает поколение (`after_flush` / `after_commit` в SQLAlchemy). Устаревший ответ не отдаётся
  никогда, явной инвалидации в коде нет.
- **Живая лента:** тот же хук публикует событие в канал пространства. SSE-поток просыпается сразу, а не через
  две секунды. Работает и для событий, которые записал воркер, — он в другом процессе.
- **Без Redis всё работает:** лимиты — в памяти процесса, кэша нет, лента опрашивает базу. Если Redis падает,
  включается пауза на 30 секунд, запросы не ждут таймаутов.
- **Очередь заданий осталась в PostgreSQL** (ADR 0002): задание и проводки, которые оно пишет, фиксируются одной
  транзакцией. Перенос очереди в Redis дал бы второй источник правды ради скорости, которая здесь не нужна.

### Метрики и ошибки
- `/api/metrics` — prometheus_client:
  - гистограмма задержек по шаблону маршрута, а не по URL, — без взрыва кардинальности;
  - счётчики ответов и отказов по лимитам.
- Очередь, пульс воркера и расход на модели собираются из PostgreSQL в момент сбора, поэтому API и воркер не расходятся.
- `docker compose --profile observability` поднимает Prometheus и Grafana с дашбордом из `infra/grafana`.
- Раздел консоли «Эксплуатация» показывает те же цифры без Grafana.
- Sentry включается переменной `SENTRY_DSN`; персональные данные не отправляются.

### Платежи
- **Сумму считает сервер** (`payment_terms`) — и при создании платежа, и повторно перед обращением к провайдеру.
- **ЮKassa, API v3:** `Idempotence-Key` на каждую запись, `capture: true`, `metadata.payment` = наш id.
  - Уведомления ЮKassa не подписаны. Поэтому тело уведомления используется только как подсказка «что-то
    изменилось»: обработчик перечитывает платёж или возврат у провайдера, сверяет сумму и `metadata`.
  - Проводка — с ключом `yookassa:<id платежа>`. Повторное или поддельное уведомление ничего не меняет.
  - Возврат проводится сторно с ключом `yookassa-refund:<id возврата>`.
- **Эмулятор ЮKassa** отвечает в форматах API, показывает страницу оплаты с тестовой картой и шлёт уведомление в
  тот же обработчик. Тестовый магазин подключается переменными `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`.
- **Telegram Payments:** `createInvoiceLink` → `openInvoice` в Mini App.
  - `pre_checkout_query` проверяет сумму и статус.
  - `successful_payment` проводит платёж по `telegram_payment_charge_id`.
  - Включается тестовым токеном провайдера из BotFather (`TELEGRAM_PAYMENT_TOKEN`).

## Последствия

- Redis на сервере занимает около 10 МБ (лимит 32 МБ, вытеснение LRU, без записи на диск).
- Метрики задержек живут в одном процессе API. При нескольких воркерах uvicorn понадобится multiprocess-режим
  prometheus_client.
- Эмулятор хранит свои платежи отдельно от данных стенда, как настоящий провайдер. Воркер удаляет такие строки
  старше недели — это дольше любого окна повторов.
